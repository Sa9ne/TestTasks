# Сервис скачивания и анализа файлов

## Как запустить

### 1. Поднять Postgres

В папке лежит `docker-compose.yml` — база с уже правильными логином/паролем
из настроек по умолчанию в `app.py`, ничего вручную создавать не нужно.

```bash
docker compose up -d
```

Проверить, что поднялась и готова принимать соединения:

```bash
docker compose ps
```
(в колонке STATUS должно быть `healthy`)

### 2. Установить зависимости и запустить сервис

```bash
pip install -r requirements.txt

API_BASE_URL="https://<хост из вашего задания>" \
python -m uvicorn app:app --reload --port 8000
```

`DATABASE_URL` можно не задавать — по умолчанию сервис подключается к базе
из docker-compose (`postgresql://fileservice:fileservice@localhost:5432/file_service`).
Если Postgres поднят иначе — передайте свой:

```bash
DATABASE_URL="postgresql://user:pass@host:5432/dbname" ...
```

При старте приложение само создаёт нужную таблицу (`CREATE TABLE IF NOT EXISTS`),
никаких миграций накатывать не нужно.

### 3. Открыть UI

http://localhost:8000

### Остановить / сбросить всё

```bash
docker compose down        # остановить Postgres, данные останутся в volume
docker compose down -v     # остановить и стереть все скачанные данные
```

## Единственное, что нужно подставить самому

Хост тестового API (`API_BASE_URL`) — в присланной Swagger-документации
указаны только относительные пути и `/openapi.json`, самого адреса там нет.
Схема запросов/ответов (`file_names` как ключ везде, `Retry-After` для 429/403)
уже сверена с реальным `openapi.json` и зашита в код.

Есть ещё два admin-эндпоинта в API (`DELETE .../progress`,
`DELETE .../throttling`) для сброса прогресса/бана по токену — в сервис не
встроены, но можно дёрнуть вручную через `/docs`, если во время
тестирования словите 403 и не хотите ждать 30 минут.

## Что где лежит

- `app.py` — весь бэкенд: клиент к внешнему API с обработкой 429/403 и
  `Retry-After`, фоновая задача скачивания, эндпоинты для прогресса,
  списка файлов (сортировка + пагинация) и расчёта статистики. Все скачанные
  файлы и их содержимое хранятся в PostgreSQL — переживают рестарт сервиса.
- `static/index.html` — одностраничный фронт на vanilla JS (без сборки):
  вкладка "Скачивание" и вкладка "Файлы и расчёты".
- `docker-compose.yml` — Postgres с volume для персистентности.

## Архитектурные упрощения (осознанные, чтобы уложиться в срок)

- Прогресс *текущего запуска* скачивания (статус/счётчики) — в памяти
  процесса, не в БД. Это осознанно: это эфемерные данные о живом процессе,
  а не то, что нужно переживать рестарт. Сами файлы и их содержимое —
  в Postgres, и это переживает рестарт.
- Один воркер uvicorn (по умолчанию). Несколько воркеров дали бы несколько
  независимых `progress` в памяти — для теста это не нужно.
- Прогресс скачивания — через polling (`GET /api/progress` раз в секунду),
  не websocket.
- "N" в прогрессе — это количество имён файлов, увиденных к текущему
  моменту (API не сообщает общий размер каталога заранее), поэтому N растёт
  по мере скачивания, а не является финальным числом до конца процесса.
- "Выбрать все" (по-настоящему все, не только текущая страница) при расчёте
  делает один дополнительный запрос со `page_size = total`, чтобы получить
  полный список имён — переживёт объём файлов тестового задания, но не
  рассчитан на десятки тысяч записей.
